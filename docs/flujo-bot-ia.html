Flujo de Usuario y Bots en Traza Backend

Documento de explicación funcional y técnica del backend orientado a tareas, delegaciones y automatización mediante bots/IA.

1. Objetivo del sistema

Traza Backend administra operaciones vinculadas a bodegas, usuarios, tareas, eventos, trazabilidad y cumplimiento. Dentro de ese ecosistema, la API de IA permite que un bot o agente externo opere sobre el sistema de forma controlada, especialmente en contextos conversacionales como WhatsApp.

Idea central: el bot no reemplaza al usuario humano. El bot actúa en nombre del usuario humano únicamente cuando ese usuario le otorgó una delegación válida.

2. Actores principales

Actor Rol dentro del sistema
Admin del sistema Crea bots, administra usuarios y mantiene la plataforma.
Usuario humano Responsable real del negocio. Pertenece a una o más bodegas, recibe tareas y puede delegar permisos al bot.
Bot / Agente IA Interfaz automatizada que conversa, consulta datos, crea tareas, guía cargas y cierra procesos permitidos.
Backend Valida autenticación, roles, delegaciones, visibilidad y persiste toda la operación.

3. Por qué existen los bots

Los bots existen para habilitar una capa de automatización sobre el backend. En vez de obligar a que toda interacción ocurra desde una interfaz tradicional, el sistema permite que una conversación por WhatsApp o un agente de IA consuma endpoints especializados y ejecute acciones reales dentro de Traza.

En la práctica, el bot sirve para:

  • Identificar usuarios por WhatsApp.
  • Solicitar o confirmar delegaciones.
  • Listar y crear tareas.
  • Contactar operarios.
  • Guiar cargas parciales de información.
  • Validar datos contra un esquema esperado.
  • Finalizar tareas y dejar trazabilidad de cada acción.

4. Qué hace el usuario humano

El usuario humano sigue siendo la autoridad principal del flujo.

  • Existe como usuario del sistema.
  • Puede pertenecer a una o varias bodegas.
  • Puede tener roles globales o roles dentro de una bodega.
  • Puede recibir tareas o formar parte de procesos productivos.
  • Puede autorizar a un bot para que actúe en su nombre.
Conclusión operativa: el humano conserva la responsabilidad; el bot solamente automatiza la ejecución.

5. Qué hace el bot

El bot es una cuenta especial con rol bot_agent. Se autentica como cualquier usuario, pero su superficie de trabajo está orientada a integraciones externas. A través de la API /api/ia/*, el bot puede operar dentro de un marco de permisos acotado.

El bot puede:

  • Consultar su propia identidad y sus delegaciones activas.
  • Buscar usuarios por WhatsApp.
  • Consultar catálogos de bodegas, fincas, cuarteles, campañas, protocolos e insumos.
  • Crear tareas cuando dispone del permiso adecuado.
  • Contactar a un usuario respecto de una asignación.
  • Guardar avances parciales en una tarea.
  • Cerrar una tarea cuando los datos están completos.

6. Concepto de delegación

La delegación es el mecanismo que conecta al bot con la autoridad de un usuario humano. Sin delegación, el bot no debería ejecutar acciones sensibles en nombre de ese usuario.

Una delegación define:

  • Qué bot recibe el permiso.
  • Qué usuario humano otorga ese permiso.
  • Si la delegación aplica a una bodega específica o es global.
  • Qué scopes o acciones quedan habilitados.
  • Si la delegación vence o permanece activa hasta ser revocada.

Scopes frecuentes

  • tareas.crear
  • tareas.ver
  • tareas.contactar
  • tareas.cargar_datos
  • tareas.resolver
  • cuarteles.crear
  • vasijas.crear

7. Flujo general del sistema

[Admin del sistema] | | crea v [Bot / Agente IA] | | hace login v [API /api/ia/*] | | identifica a un usuario humano v [Usuario humano] | | delega permisos v [BotDelegation] | | habilita acciones v [Bot] | | consulta catálogos / tareas / contexto | crea tareas / guarda progreso / finaliza v [Base de datos + logs de auditoría]

8. Flujo detallado paso a paso

8.1. Creación del bot

  1. Un administrador del sistema crea un usuario bot.
  2. Ese usuario recibe el rol bot_agent.
  3. Desde ese momento el bot puede autenticarse programáticamente.

8.2. Login del bot

  1. El bot envía email y contraseña.
  2. El backend devuelve access_token y refresh_token.
  3. Ese token se usa para consumir los endpoints de IA.

8.3. Identificación del usuario humano

  1. El bot recibe un mensaje o pedido desde WhatsApp.
  2. Busca al usuario humano por número telefónico.
  3. El backend devuelve sus datos, bodegas y delegaciones activas hacia ese bot.

8.4. Delegación manual o conversacional

Hay dos formas principales de obtener permiso:

  • Manual: el usuario autenticado crea la delegación directamente.
  • Conversacional: el bot solicita un código, el humano lo confirma y se crea la delegación.

8.5. Operación del bot con permisos válidos

  1. El bot consulta catálogos y contexto operativo.
  2. Si necesita iniciar trabajo, crea una tarea o ubica una existente.
  3. Si la tarea requiere captura progresiva, el bot guarda borradores parciales.
  4. Cuando la información queda completa y válida, el bot finaliza la tarea.

9. Flujo de una tarea con IA

[Usuario / Encargado por WhatsApp] | | "Necesito registrar un riego" v [Bot / IA] | | busca usuario + verifica delegación v [POST /api/ia/tareas/iniciar] | | crea tarea o solicita delegación v [Tarea + TareaAsignacion] | | consulta contexto v [GET /api/ia/tareas/:id/contexto] | | pide datos faltantes v [POST /api/ia/tareas/:id/guardar-progreso] | | valida contra un schema v [validation.canClose = true] | | finaliza v [POST /api/ia/tareas/:id/finalizar]

9.1. Inicio de creación de tarea

El endpoint de inicio de tarea revisa si el bot ya posee una delegación activa para el usuario identificado por WhatsApp. Si existe una delegación con scope tareas.crear, la tarea se crea de inmediato. Si no existe, el flujo devuelve un estado de “delegación requerida” y genera un código de confirmación.

9.2. Consulta de contexto

Una vez que la tarea existe, el bot puede obtener un contexto ampliado: datos de la tarea, historial previo del bot, tipo de evento inferido y esquema de entrada esperado. Esto permite que el agente converse con el usuario de forma guiada.

9.3. Guardado de progreso

La carga no tiene que ocurrir de una sola vez. El bot puede enviar borradores parciales con los campos disponibles en cada momento. El backend valida esos borradores contra un esquema y devuelve:

  • Campos requeridos faltantes.
  • Campos inválidos.
  • Progreso total sobre los campos obligatorios.
  • Una sugerencia de siguiente acción.

9.4. Finalización

Cuando los datos ya están completos y el bot dispone del permiso tareas.resolver, puede cerrar la asignación. Ese cierre deja registros de auditoría y estado final de la tarea.

10. Qué significa que todo quede auditado

Cada operación importante del bot genera registros internos. Esto permite reconstruir:

  • Qué bot actuó.
  • En nombre de qué usuario humano actuó.
  • Con qué delegación lo hizo.
  • Sobre qué tarea o asignación operó.
  • Qué payload de entrada recibió y qué resultado produjo.
Valor de negocio: la automatización no sacrifica control. El sistema conserva trazabilidad operativa y responsabilidad humana.

11. Resumen conceptual

Concepto Significado
Humano Autoridad y responsable del negocio.
Bot Operador automatizado para integraciones y flujos conversacionales.
Delegación Permiso explícito que habilita al bot a actuar en nombre de un humano.
Tarea Unidad concreta de trabajo que puede ser creada, seguida y cerrada.
IA / WhatsApp Canal de interacción, no fuente de autoridad.

12. Frase final para comunicar el modelo

El usuario humano autoriza, el bot ejecuta, la API controla y la tarea registra el trabajo.
